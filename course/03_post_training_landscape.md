# 03 · The post-training landscape: every way to change a pre-trained model

> **Why this chapter:** "fine-tuning" is really a family of methods with different data, losses and failure modes.
> Choosing the right one is the most consequential decision of a project. This chapter is the map; later chapters
> zoom in on each region.

## 1. What post-training buys you

OpenAI's InstructGPT paper (Ouyang et al., 2022) is the classic demonstration: labelers preferred outputs of a
**1.3B** model after post-training (SFT → reward model → PPO) over the raw **175B** GPT-3. The knowledge was
already in the base model; post-training made it *usable*.

That leads to the **superficial alignment hypothesis** (LIMA, Zhou et al., 2023): almost all knowledge comes from
pre-training; alignment mostly teaches *which format and style to answer in*. LIMA fine-tuned a 65B base model
on just **1,000** carefully curated examples and got a strong assistant. Supporting evidence: after alignment,
the token distribution shifts mainly on stylistic tokens ("Sure", "Here's", list markers), not on content
(Lin et al., 2023). Keep this in mind: post-training is mostly about **behavior**.

## 2. The methods

| Method | Data | Loss / signal | Teaches | Used in |
|---|---|---|---|---|
| **Continued pre-training (CPT)** | raw domain text | next token, all tokens | domain vocabulary and knowledge, new languages | code/medical/legal models |
| **Supervised fine-tuning (SFT)** | (prompt → ideal response) | next token on the response | format, task, style, "how to answer" | everything; **Projects 1 & 2** |
| **Preference optimization** (RLHF-PPO, **DPO**, KTO, ORPO…) | (prompt, chosen, rejected) | make chosen more likely than rejected | quality *judgments* that are hard to demonstrate | chat models; **Project 2** |
| **RL with verifiable rewards (RLVR)** (PPO, **GRPO**, RLOO…) | prompts + a checker program | reward from executing/checking the answer | reasoning, accuracy on checkable tasks | reasoning models; **Bonus A** |
| **Distillation** | teacher model outputs or logits | imitate the teacher | compress a big model's skill into a small one | small open models |
| **Model merging** | two or more fine-tuned checkpoints | weight arithmetic, no training | combine skills cheaply | SmolLM3, many community models |

### SFT: imitation
You show the model what a good answer looks like and minimize cross-entropy on it. It's simple, stable and the
first step of nearly every pipeline. Its limits: the model can only become as good as the demonstrations,
every token counts equally (a single wrong fact costs the same as a style choice), and it never sees
*negative* examples. SFT does not learn "don't do this".

### Preference optimization: judgment
Often it's easier to say which of two answers is better than to write the perfect one. Preference methods use
pairs (chosen ≻ rejected). Classic **RLHF**: train a reward model on the pairs, then optimize the policy with RL
(PPO), with a KL penalty that keeps it near the SFT model. **DPO** (2023) showed the same objective can be
optimized directly on the pairs with a simple classification-style loss: no reward model, no sampling. Details
are in chapter 10.

### RLVR: learning from consequences
For math, code and anything else with a checkable answer, you don't need human labels at all: sample answers,
run a checker, reward the correct ones. **GRPO** (DeepSeekMath 2024, made famous by DeepSeek-R1 in 2025) does
this efficiently by comparing answers within a group. It's what produced today's "thinking" models (chapter 12).

### Distillation: borrowing a bigger brain
- **Sequence-level:** generate answers with a strong teacher, then SFT the student on them. Most open
  instruction datasets are built this way. (Capybara, which we use, was generated by GPT-4-class models.)
- **Logit-level:** train the student to match the teacher's full next-token distribution (KL divergence), which
  carries more information per token ("dark knowledge"). Requires a shared tokenizer; TRL has a
  `DistillationTrainer`. Qwen3's small models were made with strong-to-weak distillation from larger Qwen3 models.

## 3. How real pipelines combine them

```
            ┌──────────── pre-training ────────────┐   ┌────────────── post-training ──────────────┐
raw text →  pre-train → mid-train/anneal → long-ctx  →  SFT → preference opt. → RL (verifiable) → merge
            (trillions of tokens)                       (10⁵–10⁷ examples)
```

- **Tulu 3** (AI2, 2024, fully open recipe): SFT → DPO → RLVR.
- **DeepSeek-R1** (2025): small "cold-start" SFT on long chains of thought → large-scale GRPO → rejection-sampled
  SFT → RL again. **R1-Zero** skipped SFT entirely and reasoning still *emerged* from RL on a strong base.
- **SmolLM3** (HuggingFace, 2025, open recipe): mid-training on reasoning data → SFT → APO (a DPO variant) →
  model merging to recover long-context ability.
- **Qwen3** (2025): long-CoT cold start → reasoning RL → "thinking mode fusion" (one model that can think or
  not) → general RL. Small models were distilled from the big ones.

**Project 2 rebuilds the first half of this pipeline in miniature:** base → SFT → DPO.

## 4. Choosing the starting checkpoint

| Start from | When | Watch out |
|---|---|---|
| **Instruct/chat model** | narrow task on top of general chat; little data; you want to keep its safety and instruction following | its existing format and style can fight yours; you must use **its** chat template exactly |
| **Base model** | you're building the whole post-training stack, you want full control of format, or you have lots of data | no chat template, no pad token, EOS means "end of document"; needs SFT before anything else |
| **Reasoning model** | your task benefits from thinking | training on answers *without* thinking traces can break the thinking behavior; keep data consistent with the mode you'll use |

Project 1 starts from **Qwen3-0.6B (instruct, hybrid thinking)** because we want one narrow skill on top of a
competent assistant. Project 2 starts from **SmolLM3-3B-Base** precisely to experience the raw base model.

## 5. Forgetting: the price of fine-tuning

Updating weights for task A can degrade unrelated ability B: **catastrophic forgetting**. Fine-tune a chat
model hard on JSON extraction and it may start answering *everything* in JSON. Mitigations, roughly in order
of cost:
1. **LoRA instead of full fine-tuning**: fewer, low-rank changes ("LoRA learns less and forgets less",
   Biderman et al., 2024).
2. **Lower learning rate, fewer epochs** (stop when the task metric plateaus).
3. **Mix in general data** (replay): 5–20% generic instruction data alongside your task data.
4. **Keep the adapter separate** and load it only for the task. With LoRA the base model is untouched.
5. **Measure it**: run a small general benchmark before and after (chapter 08).

## 6. A decision table

| You want… | Method | Data you need |
|---|---|---|
| a fixed output format / one task, done reliably | SFT (LoRA) | 500–10k (input, ideal output) pairs |
| a base model that chats | SFT | 10k–1M conversations |
| answers people prefer (helpful, concise, safe) | SFT then DPO | + 5k–100k preference pairs |
| better accuracy on checkable problems | GRPO / RLVR | prompts + a checker; a model that's already sometimes right |
| a small model with a big model's skill | distillation | teacher generations (mind the license) |
| domain knowledge / a new language | continued pre-training (+ SFT after) | 10⁸+ tokens of raw text |
| facts that change | **RAG, not fine-tuning** | a document store |

## 7. Licenses and provenance (boring, important)

- **Model licenses:** Qwen3, SmolLM3 and Granite are Apache-2.0. Llama uses a custom community license; Gemma has
  its own terms. Your fine-tune inherits the base model's license obligations.
- **Data licenses:** check every dataset card. Some are non-commercial; CoNLL-2003 comes from Reuters text under
  research terms, which is why this repo builds the JSON version on the fly instead of re-uploading it.
- **Distillation from APIs:** several providers' terms forbid using outputs to train competing models. Datasets
  generated from such APIs carry that question with them.
